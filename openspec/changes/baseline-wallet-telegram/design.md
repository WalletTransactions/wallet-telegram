# Design: базовая спецификация wallet-telegram

## Context

Мотивация — в `proposal.md`. Спецификации в `specs/` восстановлены по коду на
коммите `3910255` (main, 2026-10-20), вендоренному wallet-common `0.1.0
(a53e37ba)`, тестам `tests/` и `tests_integration/`, миграциям `000001`–`000002`
и `openapi.yaml`. Сверялись с `org/docs/TODO_telegram_bot.md`,
`TODO_telegram_tokens.md`, `TODO_wallet_ai.md`, OpenAPI соседних сервисов и
`wallet-infra` (compose, k8s, диаграммы).

При расхождении документа и кода источником базы считался **код**; расхождения
вынесены в раздел «Наблюдения» ниже, а не исправлены в спецификации.

## Goals / Non-Goals

**Goals:**
- Описать наблюдаемое поведение бота так, чтобы каждый сценарий можно было
  проверить тестом или ручным прогоном.
- Сохранить обоснование ключевых решений (раздел Decisions), которое иначе
  живёт только в общем TODO.

**Non-Goals:**
- Контракты соседних сервисов: описано только то, что бот вызывает и как
  трактует ответ.
- Контракт wallet-common как библиотеки: грамматика описана с точки зрения
  пользователя бота.
- Исправление найденных расхождений и любое изменение поведения.
- Запланированное, но не сделанное: фаза 4a (tool calling, MCP), несколько
  леджеров, доходы и переводы (`+`, `>`), webhook, client assertion вместо
  `X-Service-Secret` (шаг 5 `TODO_telegram_tokens.md`, отложен), порядок
  кандидатов по частоте (см. Р3).

## Decisions

### D1. Бот — ещё одно устройство пользователя
Бот пишет через `POST /sync/push` и читает через wallet-report от имени
пользователя, а не через собственный доступ к базе кошелька. Так бесплатно
достаются `seq`, проверка ссылок и ролей, идемпотентность по `batch_id` и
доставка на телефоны. Отвергнуто: прямая запись в БД (вторая реализация
write-стороны и отдельная DB-роль). Источник: TODO §1.1.

### D2. Связка в google-auth, токены не хранятся
Изначально бот хранил зашифрованный refresh-токен (миграция `000001`). Решение
2026-09-30: связка `tg_user_id → user_id` живёт в google-auth, бот берёт
5-минутный токен на команду со scope только на чтение отчётов, создание
операций и ИИ. Скомпрометированный бот не получает долгоживущих секретов, а
отключение из веба действует сразу. Источник: `TODO_telegram_tokens.md`,
«Решения» 1–2, 8; миграция `000002`.

### D3. Подключение одноразовым кодом через deep link
Веб выдаёт код, ссылка `t.me/<bot>?start=<код>` приносит его в `/start`, бот
меняет код на связку по внутреннему каналу с общим секретом, минуя гейтвей.
Пользователь ничего не вводит. Источник: TODO §1.2.

### D4. Long polling, один экземпляр, обработка в потоке поллинга
Long polling нужен только исходящий HTTPS, поэтому бот работает в LAN без
публичного адреса. Два `getUpdates` на один токен невозможны, отсюда
`replicas: 1`. Апдейты обрабатываются по одному в потоке поллинга, без пула
воркеров: при одном экземпляре это и даёт порядок. Медленный ИИ вынесен в
асинхронные задания (D8), чтобы не задерживать других. Источник: TODO §1.3,
§1.5 и «Отличия реализации шага 4».

### D5. Своя база только для настроек; эфемерное — в памяти
В базе `wallet_telegram` хранятся настройки чата и offset. Черновики, кеш
справочника (60 с), токены и ожидающие задания ИИ держатся в памяти процесса:
при одном экземпляре потеря при рестарте допустима (кнопки ответят «устарел»).
Redis отложен до появления пула воркеров. Зеркала DDL в `schema/` нет, как у
`perf`. Источник: TODO §1.4, комментарии `drafts.hpp`.

### D6. Всегда подтверждение, только создание, без отмены
И строгий формат, и ИИ ведут к карточке и записи по кнопке. Бот только
создаёт операции, отмены записанного нет, поэтому `tg_last_op` не нужна.
Источник: TODO «Открытые вопросы» (решено 2026-09-29), §3.3.

### D7. Идемпотентность детерминированными UUIDv5
`batch_id` и uuid операции выводятся из имени бота, `tg_user_id` и `update_id`
сообщения в постоянном пространстве имён. При неизвестном исходе черновик
замораживается, и повтор идёт тем же батчем: ответ wallet-api на повтор
безопасен. Перед первой записью справочник сверяется свежим, потому что
удаление на телефоне мягкое и без сверки трата ушла бы на удалённую
категорию. Источник: TODO «Подшаг 4 подробно».

### D8. LLM — в отдельном сервисе wallet-ai, асинхронно, с запасным ответом
С 2026-10-11 LLM-часть живёт в wallet-ai. Бот создаёт задание `parse_expense`
и опрашивает его сам между апдейтами. Любой сбой ИИ даёт ответ, идентичный
ответу без ИИ. Инвариант «LLM никогда не пишет в кошелёк» соблюдается тем, что
результат — только черновик. Источник: TODO (шапка), `TODO_wallet_ai.md`.

### D9. Разбор траты — в общей библиотеке
Грамматика, разрешение имён и форматирование вынесены в wallet-common
(вендорится в `third_party/`): те же правила нужны wallet-ai для проверки
ответа LLM. В спецификации бота грамматика описана как пользовательское
поведение. При обновлении вендоренной копии её нужно сверять с
`expense-strict-input` и `expense-draft`.

### D10. Границы этой базы
Внешние сервисы описаны с точки зрения бота (вариант 1 исследования). Разбиение
на capability следует потоку пользователя: приём апдейтов → связка → чтение →
ввод → черновик → запись, плюс ИИ и эксплуатация. Так изменения обычно
затрагивают одну-две спецификации.

## Risks / Trade-offs

- [Состояние в памяти] Рестарт или выкатка теряет черновики и ожидающие
  задания ИИ → для черновиков это принято (D5); для ИИ см. Р6.
- [Детерминированные id зависят от `TELEGRAM_BOT_USERNAME`] Смена имени бота
  при неизвестном исходе записи даст новый батч и возможный дубль → считать
  имя бота неизменяемым или вынести основу id в отдельную константу (Р8).
- [Вендоренная библиотека] Обновление wallet-common может молча изменить
  грамматику → сверка спецификаций при `vendor.sh`, тесты `test_strict`,
  `test_resolver`, `test_text` в этом репозитории.
- [База отстаёт от кода] Спецификация снята на конкретный коммит → задачи
  сверки в `tasks.md`; дальнейшие изменения поведения идут через changes.

## Migration Plan

Кода и данных изменение не касается. После сверки (`tasks.md`) change
архивируется: спецификации переносятся в `openspec/specs/`, этот документ
остаётся в `openspec/changes/archive/`. Откат — удалить созданные спецификации.
